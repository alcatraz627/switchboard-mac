### Plugs (Home tab)

Explored 2026-09-29, listening only. The three plugs decode (with Tuya's public
broadcast key) as one product (`productKey keyjup78v54myhan`), **protocol 3.4**,
already bound to a cloud account: .6 `d71767b54e44bcdf7aon6h`, .7
`d740139ff14a82a71esvq2`, .8 `d739196c2521acde50m6se`. Protocol 3.4 signs every
local command with the plug's own 16-character local key, so the keys are
needed once, whatever the route. The owner does not want a developer account.
The routes, best first:

1. **QR login with the Smart Life app, no developer account** (recommended).
   Tuya's official `tuya-device-sharing-sdk`, the one Home Assistant's Tuya
   integration uses, logs in by showing a QR code that the owner scans and
   confirms in the Smart Life (or Tuya Smart) app. It returns every device on
   that account with its local key. One scan, once; after that Switchboard
   talks to the plugs only on the LAN. Works only if the plugs live in a Smart
   Life or Tuya Smart account. If they were paired in a Smartivity-branded
   app, reset each plug (hold its button about 5 s) and add it in Smart Life
   first, which needs only the free app login.
2. **Flash local firmware** (Cloudcutter to OpenBeken): no keys, no cloud ever,
   but plug-model specific and can brick a plug. Only if route 1 is impossible.
3. Developer account (iot.tuya.com + `tinytuya wizard`): ruled out by the owner.

Build for route 1: a "Connect plugs…" button on the Home tab shows the QR code
in the panel; the keys land in Switchboard's state folder (mode 0600). Control
then uses `tinytuya` (protocol 3.4). Both packages would live in a private
Python environment under `~/Library/Application Support/Switchboard/` created
on first use, since the system Python the app runs has neither.

With keys, a `plugs.py` helper mirrors `wiz.py` (discover, set on/off, read
power draw where the plug reports it), and the Home tab gets a Plugs card
under Lights. Offline tests exercise the helper's validation the same way the
bulb tests do.

### allow / ask / block

Today "ask" is not a generic mode: `guard-policy.sh` handles exactly one ask
(`git.push_main`, which borrows the push gate's approval token), and every
other value is allow or block. Turning more switches into three-way choices
needs one general approval channel first:

- On an "ask" policy, the hook blocks the call and prints
  `approve <key> <nonce>` for the owner to type back, the same shape the push
  gate uses. A prompt hook writes a single-use sentinel; the retried call
  consumes it.
- The Needs-you strip (v2 plan) shows the pending ask with Approve and
  Discard, writing the same sentinel.

Candidates, in the order they would benefit: `slack.post`, `linear.write`,
`github.write`, `deploy.vercel`, `deploy.cloudflare`, `git.push`.
`github.comment`, `git.commit` and the two file guards stay two-way. This is a
change to gcc hooks and the policy registry, not only to this app.

## New areas

### Remote (csync), a new tab

csync already answers the panel's question in one call: `csync status --json`
returns the hosts plus relay, Funnel and Tailscale health.

| Row | Source | Actions |
|---|---|---|
| Console health (relay, Funnel, Tailscale) | `csync status --json` | "Fix" runs `csync doctor --fix` |
| One row per connected host | same | screenshot (opens it), open a shell in Ghostty, teardown (asks first) |
| Open invites | same | copy the invite line, revoke |
| New host | — | "Invite…" mints the line and copies it |

Every write goes through the csync CLI, so the terminal and the panel can never
disagree. Hidden when csync is not on the PATH. **Q4** asks what "ipc=csync,
Codex instance parity" meant in the backlog.

### Git status across ~/Code, a Machine group or its own tab

A scan (cached, refreshed on panel open, off the main thread) of git
repositories under the chosen roots, depth 3, skipping `node_modules` and
`.git` internals. Per repo: branch, dirty file count, ahead/behind the
upstream, stash count, worktrees. The list shows only repos that need
attention (dirty, unpushed, detached, stale worktree); a summary row counts
the clean ones.

Actions: open in Finder, in the terminal, in the editor; `git fetch`;
`git worktree prune` (asks first). No commit, push or reset from the panel,
ever. **Q5** sets the roots.

### Connected devices and drives, a Machine group

`diskutil list -plist` and `diskutil info -plist` give every external and
disk-image volume with mount point, format, size and free space. Rows: one per
external volume. Actions: open, eject (`diskutil eject`), reveal the disk in
Disk Utility. Formatting and erasing are out of scope: too destructive for a
one-click panel.

### Wi-Fi, Bluetooth, sound and brightness, a new "Controls" tab

The goal is to hide the separate menu bar items, so each row must match what
Control Center does.

| Control | How | Catch |
|---|---|---|
| Wi-Fi on/off, current network, switch network | CoreWLAN | macOS 14+ hides the network name from any app without Location Services permission. **Q6**. |
| Bluetooth on/off, connected devices, connect/disconnect | IOBluetooth, or `blueutil` | `blueutil` is a Homebrew install; the framework route needs no install. |
| Output device, volume, mute | CoreAudio | none |
| Built-in display brightness | the DisplayServices private API | private API: fine for a personal app, would block App Store distribution (not planned) |
| External display brightness | DDC over the cable (`m1ddc`) | Homebrew install; some monitors ignore DDC. **Q6**. |

### Disk and cleanup

Belongs in sys-monitor, not here. A note was left there (see

## Proposed build order

Each step ships as its own minor release with snapshots in both appearances.

1. Hooks tab and Dev servers (v2 plan): no new permissions, highest daily use.
2. Remote (csync) tab: read-only first, then actions.
3. Drives group, then Git status.
4. Controls tab: audio first (no permission), then Bluetooth, Wi-Fi, brightness.
5. Plugs, once keys exist (Q2).
6. Needs-you strip with the generic ask channel (Q3): last, because it touches
   live gates in gcc.
