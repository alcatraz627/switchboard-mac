### Plugs (Home tab)

Reading the keys from the Lifelong Smart app on the phone did not work: the
phone is not rooted, so adb cannot read the app's private data.

Explored 2026-09-29, listening only. The three plugs decode (with Tuya's public
broadcast key) as one product (`productKey keyjup78v54myhan`), **protocol 3.4**,
already bound to a cloud account: .6 `d71767b54e44bcdf7aon6h`, .7
`d740139ff14a82a71esvq2`, .8 `d739196c2521acde50m6se`. Protocol 3.4 signs every
local command with the plug's own 16-character local key, so the keys are
needed once, whatever the route. The owner does not want a developer account,
and the plugs are paired in **Lifelong Smart**, a branded Tuya app.

1. **QR login with the Smart Life app** (recommended). Tuya's
   `tuya-device-sharing-sdk`, which Home Assistant uses, logs in by a QR code
   the owner confirms in Smart Life and returns every device with its local
   key. It covers only Smart Life and Tuya Smart accounts, so each plug moves
   there first: hold its button about 5 s until it blinks, add it in Smart
   Life. After one scan Switchboard talks to the plugs only on the LAN.
2. **Flash local firmware** (Cloudcutter to OpenBeken): no keys, no cloud, but
   model specific and can brick a plug.
3. Developer account (iot.tuya.com + `tinytuya wizard`): ruled out.

Build for route 1: a "Connect plugs…" button on the Home tab shows the QR code
in the panel; keys land in Switchboard's state folder (mode 0600). Control uses
`tinytuya` from a private Python environment under
`~/Library/Application Support/Switchboard/`. A `plugs.py` helper mirrors
`wiz.py`, and the Home tab gets a Plugs card under Lights.

### Scroll-to-cycle quick pages (owner idea, 2026-10-01; built on branch `scroll-to-cycle`)

Built as specified below, with these readings: pages are Now, Limits,
Approvals, Bulbs, Pinned notes (notes gained a pin); scrolling the way that
moves a list down goes forward and wraps; one page per swipe or wheel notch;
the 3 s linger applies to every page, the plain card included (owner to
confirm); the status-chip row holds three, the count that always fits.
Validation report: `.claude/output/20261001-scroll-to-cycle-validation/validation.md`
(ISSUES-FOUND, all fixed in ddbb5d4). Unconfirmed without a live pointer:
that a real scroll reaches the icon, and first-click on the card's buttons.

The original idea:

Hovering the menu bar icon shows the default popover, as now. Scrolling with the
mouse over the icon itself (not over the popover) cycles the popover through a
few pages the owner reaches for often: limits, approvals, bulbs, pinned notes.
The popover stays up for 3 s after the mouse leaves.

Each cycled page shows its active things at full width, in the same sort order
as the main tab. Everything inactive is compressed into one or two rows of small
chips, each with an icon and a short label, in the same type and style as the
rest of the kit. Clicking a chip makes it active, so it moves into the list; each
active row has a way to turn it off again. Bulbs: on bulbs are rows, off bulbs
are chips you click to switch on. Notes: only pinned notes show as rows. Every
cycled page carries a button that opens the full tab, but the reduced set can be
tweaked from the popover alone.

The default page gains a single row of small status chips for things that need
the owner, such as an approval waiting or an alert. Each chip has its own colour
and icon, a tooltip, and opens its page on click. Chips keep their natural width
(never stretched), and the row holds a fixed count that always fits (3 to 5; pick
the number that fits every time).
